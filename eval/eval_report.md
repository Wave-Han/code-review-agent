# Code Review Agent 评估报告

> 生成日期:2026-10-24 · 所有数字来自 `run_eval.py` 真实运行(离线模式,seed=42)
> 配套代码:本目录 `eval_harness.py` / `test_cases_v2.py` / `run_eval.py`,单元测试见 `tests/test_detector_exemptions.py`

## 1. 摘要

本轮评估完成了一个完整的「基线 → 改进 → 复测」闭环:

| 指标(miss=0,30 用例 × 5 次) | v2 基线 | v2 改进后 | 变化 |
|---|---|---|---|
| Precision | 90.0% | **100.0%** | +10.0pp |
| Recall | 100.0% | **100.0%** | 持平 |
| F1 | 90.0% | **100.0%** | +10.0pp |

改进手段:给检测规则加三层**上下文感知豁免**。Precision 提升 10 个百分点,Recall 零损失;v1 测试集回归 100% 无破坏;噪声下一致性 +10pp 且可被机制精确归因(见 §7)。

## 2. 被评估对象与诚实声明

被评估对象是 `eval_harness.py` 中的 **Detector(离线规则引擎)**,它作为 Agent 检测能力的**确定性替身**(regression proxy):

- 真实 Agent 走 LLM,输出有随机性;Detector 用正则规则模拟其检测行为,便于离线、可复现地迭代评估方法本身
- `miss_prob` 参数人为注入漏检概率,模拟 LLM 非确定性,用于一致性研究
- **结论的适用范围**:本报告证明的是「评测方法 + 改进方法论」的有效性(评测集设计 → 基线 → 定向改进 → 复测),不是某个线上 Agent 的真实准确率。接入真实 LLM 后端(`LLMJudge` 在线模式)是后续工作。

## 3. 评测集

### v1(Python,6 用例)——方法论验证集

4 类缺陷各 1 条 + 1 干净 + 1 多重缺陷。用途:验证评估流水线正确性(完美 Detector 应得满分)。

### v2(Java,30 用例)——主评测集

按「缺陷测召回 / 干净+陷阱测精确率」的压力设计:

| 构成 | 数量 | 压力方向 |
|---|---|---|
| 缺陷用例(secret 5 / sqli 6 / empty-catch 5 / debug 4,含 3 条多重缺陷) | 20 | Recall |
| 干净对照(环境变量取密钥、参数化查询、日志规范…) | 6 | Precision |
| 陷阱用例(长得像缺陷的合法代码) | 4 | Precision |

4 个陷阱用例的设计意图:基线规则**故意写宽**,让陷阱必然引爆 FP,给 Precision 留出可改进空间——这是评估驱动改进的实验前提。

## 4. Rubric(指标定义)

| 指标 | 定义 | 含义 |
|---|---|---|
| Precision | TP/(TP+FP),逐用例算 P 后取宏平均 | 报告里多少是真问题(不报假警) |
| Recall | TP/(TP+FN),同上宏平均 | 真问题多少被找到(不漏报) |
| F1 | P、R 调和平均 | 综合指标 |
| Severity Accuracy | 检出类别中严重级别与标注一致的比例 | 分级是否正确 |
| Consistency | 同一用例多次运行检出集合相同的比例 | 结果稳定性(LLM 随机性的代价) |

**聚合方式说明(宏平均 vs 微平均)**:本框架按用例取宏平均。基线噪声实验中出现过「噪声加大、宏平均 Precision 反而升高到 94%」的反直觉现象——陷阱用例的 FP 偶尔被随机 miss 跳过,该用例 P 从 0 变 1,拉高宏平均。教训:**聚合方式本身就是设计决策**,报告数字必须注明口径。

P 90.0% / R 100% / F1 90.0% / 一致性 100%。

3 个 FP 全部来自陷阱用例,且全部按设计引爆:

T04(logger 名叫 `debug`)未引爆,天然通过。

### v1 基线(Python,6 用例)

miss=0:P/R/F1 全 100%——流水线正确性验证通过,后续作为回归集。

## 6. 改进实验(Day 9)

**假设**:FP 的根因不是规则匹配错了,而是规则**没有上下文**。给三类 FP 对应的上下文信号加豁免,可在不损失 Recall 的前提下消除全部 FP。

**改动**(TDD:先写 3 个豁免测试看 RED,配 3 个「正例仍报」回归钉,再实现转 GREEN,pytest 6/6):

| 上下文信号(文件级) | 豁免类别 | 理由 |
|---|---|---|
| 类名 `*Test` 结尾 | hardcoded_secret | 测试夹具里的假密钥不是泄漏 |
| 存在 `static void main` | debug_print | CLI main 的 println 是程序输出 |
| `return "…SELECT…"` 字符串字面量 | sql_injection | 返回文案里的 SQL 是文档/警告 |

设计约束:**豁免刻意收窄**——过宽的豁免买 Precision 是拿 Recall 悄悄付账,所以每个豁免测试都配一个同类别正例回归钉(如「测试类豁免」配「生产类 PASSWORD 仍报」)。

**结果**(同评测集复测,miss=0,30 用例 × 5 次):P 90.0%→**100.0%**,R 保持 **100%**,F1→**100.0%**。T01–T04 逐用例全部 1.00。v1 回归 100%,无破坏。

## 7. 噪声实验(miss=0.3,模拟 LLM 30% 随机漏检)

| 指标 | v1(×5) | v2 基线 | v2 改进后 |
|---|---|---|---|
| Recall | 81.1% | 88% | 87.7% |
| Consistency | 33.3% | 43.3% | **53.3%** |

两个关键结论:

1. **一致性雪崩**:漏检率 30% 时,不足一半用例能稳定复现同一检出集合。单次运行的结果没有统计意义——真实 LLM 评估必须多轮取统计,这是「评估报告为什么必须报一致性」的实证。
2. **改进的一致性收益可精确归因**:43.3%→53.3% 恰好 +10pp = 3/30。机制:3 个陷阱用例从「命中→可能被随机跳过→波动」变成「确定性豁免→恒空检出→稳定」。改进的真实效应能从统计里算出来,而不是碰运气。

## 8. 局限与后续

| 局限 | 影响 | 后续 |
|---|---|---|
| Detector 是 regex 替身,非真实 LLM Agent | 数字不能外推为线上准确率 | 接入真实模型,LLMJudge 已预留在线模式 |
| 豁免是文件级粗粒度 | 测试类里的**真**密钥、main 里的 printStackTrace、return 拼接的真查询构建器都会被漏放 | 行级/AST 级上下文(真实工具的做法) |
| 评测集 30 条,合成代码 | 覆盖面有限,难度梯度单层 | 扩容 + 引入真实开源代码片段 |
| 宏平均口径 | 噪声下可能出现反直觉上升 | 补微平均口径双报 |
